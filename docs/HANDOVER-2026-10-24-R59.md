# 第五十九轮交接（2026-10-24）

> 主题：修用户现场报的「登陆态不保持」——刚打开程序显示未登录，去账户页转一圈再回来才显示已登录。
>
> 本轮只做代码侧验收（构建 + 单测）；真机点击与真实微软账户登录由用户执行。

## 0. 现象与根因

现象：`accounts.json` 里明明有账户，冷启动后首页卡片是「未登录」，版本页点「启动」被
「还没有账户。先到「账户」页添加一个离线账户即可启动。」挡下；进一次账户页再返回，两处都正常了。

根因不是缓存过期，是**加载时机**：`AccountService` 构造时不读盘，而旧实现里唯一调用 `LoadAsync` 的地方
是账户页（`AccountsViewModel.ReloadAsync` 里的 `_serviceLoaded` 分支，改动前在 `AccountsViewModel.cs:730-736`）。
其余消费者在首帧就读了空状态：

| 消费者 | 位置 | 后果 |
|---|---|---|
| 首页账户卡片 | `HomeViewModel.LoadAccount`（`_accounts.ActiveAccount`） | 恒为「未登录」，副标题同样是「未登录 · N 个版本可用」 |
| 版本页启动 | `VersionsViewModel` 的 `if (_accounts.ActiveAccount is null)` | 直接 return，提示「还没有账户」 |
| 三个启动入口 | `HomeViewModel` / `VersionsViewModel` / `ServersViewModel` 的 `EnsureValidActiveAccountAsync` | 返回 null，退化成「未登录」启动失败。`GameLauncher` 自己不读账户：账户由 `LaunchOptionsFactory.Build` 传进 `LaunchOptions` |

## 1. PCL2 对照

PCL2 的登录态存在设置缓存里，随启动时的 `Setup.Load()` 一起进内存，页面直接读：

- `Modules/Minecraft/ModLaunch.vb:410-470`：`McLoginAble()` / `McLoginData()` 读的是 `Settings.Get(Of McLoginType)("LoginType")`、
  `LoginLegacyName` 等已加载的配置项，不存在「进过登录页才有登录态」。
- `Pages/PageLaunch/PageLaunchLeft.xaml.vb:86`：`If McLoginAble() = "" Then McLoginLoader.Start()`——首帧就能判定能不能自动登录。

也就是说：**登录态必须在窗口建出来之前就在内存里**，这一点两边口径一致，本轮照此对齐。

## 2. 改动清单

### 2.1 Core：账户加载语义与设置对齐

| 文件 | 位置 | 改动 |
|---|---|---|
| `src/NebulaLauncher.Core/Abstractions/AccountServices.cs` | :34-47 | `IAccountService.LoadAsync` 文档改为「**幂等**，第一次之后直接返回」；新增 `ReloadAsync`（DIM，默认转调 `LoadAsync`） |
| `src/NebulaLauncher.Core/Accounts/AccountService.cs` | :38-41 | 新增 `_loadGate`（串行化读盘）与 `_loaded`（幂等标记） |
| 同上 | :104-136 | `LoadAsync` / `ReloadAsync` → `LoadCoreAsync(force)`；`force=false` 且已读过盘时直接返回；**「已加载」只在读成功时置位** |
| 同上 | :138-208 | 原 `LoadAsync` 方法体整体改名为 `LoadFromDiskAsync`，逻辑不变，只多返回一个「这次读到的结果可不可信」的 bool（文件不存在 / 解析成功 → true，异常 → false 且不置 `_loaded`） |

为什么幂等是必须的：预热之后第一次进账户页会再调一次 `LoadAsync`，不幂等就等于用磁盘旧状态
把内存里刚改完的当前账户盖回去（`SetActive` 的落盘是后台 fire-and-forget，存在真实窗口）。

为什么失败不算「已加载」：生产代码里没有 `ReloadAsync` 的调用方，账户页又会被自己的 `_loaded` 早退挡住；
把失败也标记成已加载，一次瞬时 IO 失败（文件被占用 / 半写）就让本次会话永久停在「无账户」，
接下来添加账户还会拿空表覆盖磁盘。不标记的话，进一次账户页就会重试，文件修好后自愈。
取消同理：被取消掉的那次不算读过。

### 2.2 App：首帧之前预热

| 文件 | 位置 | 改动 |
|---|---|---|
| `src/NebulaLauncher.App/Services/StartupState.cs` | 新增 1-78 | `LoadBeforeFirstFrame(IServiceProvider)`：同步加载设置与账户；单项缺失跳过，取服务与等待加载同在一个 try 里，抛异常只写 Warn 不阻断启动 |
| `src/NebulaLauncher.App/App.axaml.cs` | :52-58 | 原先内联的「同步读设置」整段替换为 `StartupState.LoadBeforeFirstFrame(Services)`，位置仍在 `new MainWindow(Services)` 之前 |

为什么必须同步、且必须在建窗口之前：首页 ViewModel 是在 `new MainWindow(Services)` 的构造链里建出来的
（`MainWindowViewModel` 构造 → `Navigate(Home)` → 页面工厂 → `HomeViewModel` → `OnNavigatedToAsync`），
异步加载晚一步，首帧就已经按空账户画完。两处 `LoadAsync` 内部都是 `ConfigureAwait(false)`，
所以在 UI 线程上 `GetAwaiter().GetResult()` 不会死锁（与设置那条既有做法同源，见 HANDOVER §6.20）。

### 2.3 App：首页在页面激活期间订阅账户事件

| 文件 | 位置 | 改动 |
|---|---|---|
| `src/NebulaLauncher.App/ViewModels/HomeViewModel.cs` | :86 | 新增 `_accountEventsAttached` |
| 同上 | :432 | `OnNavigatedToAsync` 先 `AttachAccountEvents()`，再 `LoadAsync()` |
| 同上 | :445 / :462 | `OnNavigatedFromAsync` 与 `Dispose(bool)` 调 `DetachAccountEvents()` |
| 同上 | :598-632 | `OnAccountsChanged`（`Dispatcher.UIThread.Post` 后先查 `IsDisposed`，再 `LoadAccount()` + `UpdateSubtitle()`）与 `Attach/DetachAccountEvents` |

订阅挂在页面激活期间而不是构造函数：首页是常驻缓存页，停在本页时不会再走 `OnNavigatedToAsync`，
登录完成 / 令牌续期 / 移除账户要能当场反映到卡片；而挂在构造函数里会让被 `InvalidateStalePages`
丢弃的旧页面一直留在账户服务的订阅表上。

## 4. 未验证 / 已知限制

- **真实微软账户与第三方验证账户**：本轮用例全部用离线账户落盘（`accounts.json` 的
  `activeAccountId` + 令牌字段形态一致），微软令牌的 DPAPI 解保护在预热路径上没单独跑过——
  它走的是 `LoadFromDiskAsync` 里既有的 `TokenProtector.Unprotect`，与账户页加载同一条代码。
- **点击级交互**：截图模式点不动，首页卡片「登录后立即变色」只有编译期绑定校验 + 事件链路审查，
  没有像素证据。
- **首帧耗时**：账户文件在慢盘 / 网络盘上时，预热会把窗口出现推迟到读盘完成（与设置同一代价）。
  账户文件是几 KB 的 JSON，实测无感；若将来账户令牌改成远端拉取，这里要改成异步 + 首帧占位。
- **首页截图基线变了**：`tools/seed-demo-data.ps1` 生成的数据目录上，冷启动首页两侧文案从
  「未登录 / 无账户」变成账户名（见 §3.1）。以后拿历史截图做像素对比时，这一块是**预期差异**，
  不是布局回归。
- 没有改 `settings.json` / `accounts.json` 的任何字段与语义，旧数据目录直接可用。
