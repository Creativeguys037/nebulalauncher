# Nebula Launcher v1.0.2

v1.0.1 之后的补丁版，2026-10-25 发布。主题是 GitHub issue #27 的修复：报告者反馈「下载慢、安装出错」。经查那不是单一故障，而是五个互相独立的缺陷——安装因共享清单缓存文件被并发重写而失败、设置页的「并发下载数」从未生效、手动选镜像后永不降级、安装期间装不了 Java、整合包修复必然抛 `KeyNotFoundException`。本文件由 `gh release create v1.0.2 --notes-file docs/release-notes/v1.0.2.md` 直接读取（`CONVENTIONS.md` §8.7）。

## 一、概览

Nebula Launcher 是一个以 Windows 为首发验证平台的 Minecraft Java 版桌面启动器：原生 Avalonia 界面，不内嵌 WebView，把版本安装、实例与模组管理、启动、崩溃诊断收在同一个窗口里。

### 本版包含

1. **修复 #27-A：安装不再因共享清单文件被并发重写而失败。** CmlLib 4.1.0 的 `MojangJsonVersionLoaderV2` 每次求值都用 `File.Create` 重写 `<.minecraft>/versions/version_manifest_v2.json`，不做「有缓存就跳过」；而启动器每次新建 CmlLib 启动器都得到一个独立的加载器实例，进程内没有任何跨调用互斥。安装、启动前补齐、命令行构建、修复四条链只要同一时刻有两条在跑，后到的那次写就撞 `ERROR_SHARING_VIOLATION`，表现为 `IOException: The process cannot access the file ... because it is being used by another process`。修法是给加载器加一层进程级串行化装饰器（`src/NebulaLauncher.Core/Launching/SerializedVersionLoader.cs`），在工厂里包住原有加载器（`src/NebulaLauncher.Core/Launching/MinecraftLauncherFactory.cs:67 Create`），四条链自动共享同一道闸门。只串行化「加载器求值」这一小段，不串行化文件下载——否则安装会退化成单线程，等于用缺陷 A 的修法制造出缺陷 B 那种慢。
2. **修复 #27-B：「并发下载数」真正生效。** 设置里这一项此前从未传进下载队列，也从未传进安装器：界面写着 256、实际恒跑 64，而游戏本体的逐文件下载更恒为 8。现在队列的并发上限（`src/NebulaLauncher.Core/Downloads/DownloadQueue.cs:216 MaxConcurrency`）与安装器的并发上限（`src/NebulaLauncher.Core/Installing/InstallService.cs:83 MaxParallel`）都从同一个设置值来，并由设置变更事件同步；启动前的文件补齐与命令行构建也读同一个值（`src/NebulaLauncher.Core/Launching/GameLauncher.cs ResolveMaxParallel`）。两端都夹在 1–256，且都是「批级快照」：批次进行中改设置只影响下一批。
3. **修复 #27-C：手动选镜像时，镜像劣化会在界面上提示。** 旧行为是手动档完全不采样，镜像坏了每个文件都要先撞一次连接重置再回退官方，用户只看到「很慢」却没有任何解释。现在手动档仍**不换源**（用户的选择不被自动逻辑推翻），只累计镜像连续失败，达到 3 次后在下载页状态行给出提示「镜像连续失败 3 次，可能已不可用：可在设置里改用自动或官方源」。自动档的降级逻辑与 `docs/PITFALLS.md` D9 裁决均未改动。
4. **修复 #27-D：安装进行中不再挡住 Java 运行时与 authlib-injector。** 安装期间下载队列被安装批次独占，而 Java 运行时（26.1.2 需要 Java 25+）与 authlib-injector 恰好走普通下载批次，于是被闸门抛「安装批次正在进行」——不退出安装就装不了 Java，不装 Java 就装不完游戏。新增旁路下载通道（`src/NebulaLauncher.Core/Downloads/DownloadQueue.cs:540 DownloadBypassAsync`）：照常下载与计数，但不接管任务面板、不写批次历史，因此可与安装并发；安装那几千行逐文件进度不会被 Java 的几十个文件替换掉。
5. **修复 #27-E：修复缺版本描述的实例时给出可执行说明，而不是 `KeyNotFoundException`。** 整合包导入时若没有同时安装游戏，实例目录只有 `instance.json` 没有版本 json（刻意的：写一个无父版本的版本只会让版本页多一条「损坏」）。此前对它点「修复」会调 CmlLib 安装器并抛 `KeyNotFoundException: Cannot find <名字>`，用户看到的是「安装流程未能补齐缺失文件」却不知道缺什么。现在两档修复都在入口先判定版本描述是否存在（`src/NebulaLauncher.Core/Installing/InstallService.Repair.cs RepairAsync`），缺失时给出「缺少版本描述文件 … 请在版本页为它安装游戏，或重新导入该整合包」。
6. **一处顺带的重复消除。** 普通批次与新增的旁路批次原本各复制一份调度骨架，已抽成共用内核（`src/NebulaLauncher.Core/Downloads/DownloadQueue.cs DispatchAsync`）；旁路只是不参与暂停语义。

### 系统要求

- Windows 10 1809 及以上 / x64。
- zip 形态需要 .NET 8 Desktop Runtime（<https://dotnet.microsoft.com/download/dotnet/8.0>）；便携单文件形态自带运行时，不需要。
- 至少 200 MB 可用空间，游戏版本与实例另计。
- 启动 Minecraft 需要对应版本的 Java；启动器可在缺 Java 时一键安装。

对外版本号一律 `v1.0.2`，唯一来源是 `Directory.Build.props:9` 的 `<Version>1.0.2</Version>`；它同时决定 AssemblyVersion、FileVersion 与 InformationalVersion，设置页「关于」与崩溃导出的 `system.txt` 显示同一串，发布 tag 与发布目录名也跟着它走。

## 二、安装与体积

### 附件与实测体积

体积在本机 win-x64、Release 配置下由 `build.ps1 -Publish` 构建、`tar` 打包后实测（2026-10-25，tag `v1.0.2`）：

| 附件 | 形态 | 实测体积 | 文件数 | 前提 |
| --- | --- | --- | --- | --- |
| `NebulaLauncher-v1.0.2-win-x64.zip` | 框架依赖 + 单文件，原生库外置 | 压缩包 _ZIP_BYTES_ 字节；解压后 26,517,290 字节 | 解压后 3 个 | .NET 8 Desktop Runtime |
| `NebulaLauncher-v1.0.2-win-x64-portable.exe` | 自包含 + 单文件 + 裁剪压缩 | 25,277,035 字节（单文件，无解压步骤） | 1 个 | 无 |

zip 解压后 3 个文件、合计 26,517,290 字节：`NebulaLauncher.exe` 15,298,202 字节 + `libSkiaSharp.dll` 9,414,216 字节 + `libHarfBuzzSharp.dll` 1,804,872 字节。便携形态没有解压步骤，25,277,035 字节就是那个单文件 exe。这些数字随 .NET 运行时版本与构建机变化。

### 安装与运行

- **zip**：解压到任意可写目录，双击 `NebulaLauncher.exe`。目标机缺 .NET 8 Desktop Runtime 时 Windows 会提示安装；装好后不需要 `%TEMP%` 写权限。
- **portable exe**：放到任意目录双击，无需解压、无需运行时。首次启动把原生库解压到 `%TEMP%\.net\NebulaLauncher\`；该目录被安全软件或策略拦截时启动会直接失败，改用 zip，或设置环境变量 `DOTNET_BUNDLE_EXTRACT_BASE_DIR` 指向一个可写目录。
- 两种形态共用同一份数据目录（默认 `%APPDATA%\NebulaLauncher`），可以互换使用。
- 可执行文件未签名，Windows SmartScreen 会弹「已保护你的电脑」：点「更多信息」，再点「仍要运行」。

## 三、已知限制

以下 8 条在 v1.0.2 的代码里确认存在，也是本版真正的功能缺口。每条后面的括号是代码位置指针。它们与 v1.0.1 相同：本版是补丁版，只修 #27，未触及这些缺口。

1. **页面切走后旧页面的后台任务不回收。** 实例页、模组页打开定时刷新后切到别的页面，旧页面的定时器与订阅不会被拆掉；长时间来回切换会表现为刷新变密或偶发卡顿（`src/NebulaLauncher.App/ViewModels/MainWindowViewModel.cs:322 InvalidatePageCache`）。
2. **快速连点导航时页面钩子可能交错。** 上一下一页的进入 / 离开准备工作是异步发起、不等结果的，连点左侧导航时偶发数据晚一拍，切换过快时看到的是上一页的旧数据（`src/NebulaLauncher.App/ViewModels/MainWindowViewModel.cs:417 RunPageLifecycleAsync`）。
3. **反复进出账户页会累积监听。** 账户变化通知的订阅只在页面销毁时退订，而缓存失效的路径不销毁页面，进入账户页次数越多，监听越多（`src/NebulaLauncher.App/ViewModels/AccountsViewModel.cs:265 Dispose`）。
4. **启动器运行中手改账户文件不生效。** 直接编辑 `accounts.json` 后，界面不会重新加载，需要重启启动器（`src/NebulaLauncher.Core/Abstractions/AccountServices.cs:14 ReloadAsync`；实现见 `src/NebulaLauncher.Core/Accounts/AccountService.cs:43 LoadAsync`）。
5. **按文件夹放开的资源包不被识别。** 资源包列表只认 `.zip` 与 `.resourcepack` 文件；把资源包解包成 `resourcepacks/<名字>/` 文件夹后不进列表（`src/NebulaLauncher.Core/Mods/ContentService.cs:179 ScanFiles`、`src/NebulaLauncher.Core/Mods/ContentService.cs:1192 IsContentFile`）。
6. **并发导入同名整合包可能撞名。** 实例名唯一化是先查后建，两个同名整包同时导入的极端时序下会撞到同一个版本目录名（`src/NebulaLauncher.Core/Backups/ModpackService.cs:261 ResolveUniqueVersionName`、`src/NebulaLauncher.Core/Backups/ModpackService.cs:1802 IsVersionNameTaken`）。
7. **继承型整包首次启动要补下载 client jar。** 导入的整包若引用原版版本，首启前会补一个约 20 MB 的 client jar，启动前有一条警告提示，进度停在准备阶段属于正常（`src/NebulaLauncher.Core/Backups/ModpackService.cs:340 WriteInheritedVersionJsonAsync`；告警来自 `src/NebulaLauncher.Core/Launching/PreflightChecker.cs:96 CheckLoaderAsync`）。
8. **换账户后实例面板的认证服务器文案滞后。** 已打开的实例设置面板仍显示上一个账户「跟随账户」的认证服务器，关掉面板重开或重启启动器后正确（`src/NebulaLauncher.App/ViewModels/VersionsViewModel.cs:1947 EditorAuthServerHint`）。

### 本版修掉的那条限制说明

**整合包导入后版本描述仍不写齐。** #27-E 选择的是票里两个选项中「明确报错」那一条：修复时给出可读说明，而不是在导入阶段同步写入版本 json。原因是导入侧此刻拿不到确定的父版本名，硬写一条 `inheritsFrom` 为空的版本只会让版本页多出一条「损坏」，把报错从「修复时看不懂」挪到「导入时就坏掉」。若后续要支持导入即写齐，需要先让导入流程拿到确定的父版本名，那是独立改动。

## 四、证据链与签名说明

### 签名状态

本版可执行文件未使用代码签名证书签名，因此 Windows 可能显示「Windows 已保护你的电脑」：首次运行点「更多信息」→「仍要运行」。请用上一节的 SHA256 核对文件完整性后再决定是否运行（右键 → 属性 → 数字签名 为空属预期）。

### 发布可见性

仓库为私有仓库，未登录状态下访问本 Release 的网页地址返回 404，属预期；附件仅对拥有仓库访问权限的成员可见。发布命令只建草稿（`--draft`），「Publish release」由人在网页点。

### 产物自检

三道产物自检都在构建时执行，未使用 `-SkipVerify`，两种形态各自跑满三道：

- 第 1 关 `<out>\NebulaLauncher.exe --probe-dir <out>`：30 秒内退出码 0，输出含 `writable=YES`。
- 第 2 关 `--selftest-json`：120 秒内退出码 0、输出无 `json-selfcheck.FAIL`、且 `json-selfcheck.summary=7/7`；它真跑七条 JSON 落盘往返（`src/NebulaLauncher.Core/Diagnostics/JsonSelfCheck.cs:23 JsonSelfCheck`）。
- 第 3 关 `--data-dir <out>\.verify --screenshot <out>\.verify.png --page home`：20 秒内退出码 0 且 PNG 大于 10240 字节（本版实测 145,661 字节）。

第 2 关把单文件解包目录钉在产物目录（`DOTNET_BUNDLE_EXTRACT_BASE_DIR`），它的结论只反映产物本身，不受 `%TEMP%\.net` 可写性影响。

### 本版修复的自动化证据

`tools/TestRunner` 全量 2472 项通过，其中本版新增 28 项直接对应 #27 的五个缺陷：

- 版本清单求值串行化：`tests/NebulaLauncher.Tests/CoreLaunch_VersionLoaderLockTests.cs`（并发求值时最大并发进入数为 1；另有一条对照实验证明量具不空转；闸门超时与取消可脱身）。
- 并发上限的管道：`tests/NebulaLauncher.Tests/CoreLaunch_MaxParallelPlumbingTests.cs`（工厂把 1/8/64/256 交给安装器）、`tests/NebulaLauncher.Tests/CoreDownloads_ThreadAndBypassTests.cs`（并发峰值实测、批级快照、旁路不污染安装面板、旁路不写历史、旁路不受暂停阻断）。
- 手动镜像劣化提示：`tests/NebulaLauncher.Tests/CoreDownloads_ManualMirrorHintTests.cs`（阈值前后、不换源、不产 `DegradeReason`、镜像恢复清零、切策略清空、事件只在出现与消失时各触发一次）。
- 缺版本描述的修复行为：`tests/NebulaLauncher.Tests/CoreInstalling_RepairMissingVersionJsonTests.cs`（两档给出同一份可读说明、不出现 `Cannot find` / `KeyNotFound` / 「修复中断」、判定发生在联网之前）。
